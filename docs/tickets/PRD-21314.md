## Product design

### Goals / Non-goals

**Goals (this ticket):**
- Give an MSPbots Agent platform agent live, per-request-credentialed access to a PayPal business
  account for the two capability groups that cover the most common "act on PayPal on my behalf" asks:
  1. **Checkout orders & payments** — create an order, check its status, capture payment on an approved
     order, inspect a capture, refund a capture, inspect a refund.
  2. **Invoicing** — draft an invoice, send it to a customer, look up an invoice, list invoices.
- Every call is logged with enough context to audit "what action, on which PayPal account, when" without
  ever logging or persisting the submitted credentials (ties back to the ticket's own words: "credentials
  encrypted and every action logged").
- Credentials are supplied per request (Header), never stored by the MCP service, consistent with the
  platform's existing per-tenant, stateless MCP contract.

**Non-goals (this ticket; candidates for follow-up tickets, see §7):**
- **Subscriptions** (recurring billing plans) — different object model, different dunning/retry semantics,
  not implied by anything in the ticket text beyond the generic "live access" blurb.
- **Payouts** (mass payments to third parties) — a materially higher-risk, irreversible money-movement
  surface; shipping it in the same first version as checkout/invoicing would roughly double the audit and
  test surface for a ticket that names no payout use case.
- **Disputes** (chargeback/dispute management) — read/respond-to-dispute flows are a distinct workflow
  with their own evidence-upload contract; no dispute use case is named.
- **Receiving PayPal webhooks** — this service is a stateless, per-request tool a platform agent calls; it
  does not expose a public inbound endpoint and cannot "receive" vendor webhooks without contradicting the
  no-server-side-state contract (SOP §1.3/§3.3). Only PayPal's own request/response APIs are wrapped.
- Any PayPal Agent Toolkit / "AI-ready" SDK PayPal ships itself — SOP requires clean-room implementation
  against the public REST API, not re-exporting a third-party SDK or MCP (SOP §0, rule 3).
- Any change to `agent.mspbots.ai`'s own connect-dialog UI. This ticket only builds the MCP service the
  gateway calls; how/whether PayPal appears in the platform's connector library is outside the vendor
  repo's scope.

These cuts, and the tool list below, were not dictated by the ticket — see "Decisions made by DEV01" in
the tech design; they are open to change by moving the ticket back to `5b - ready for groom` with the
desired capability named.

### Capabilities (AC1–AC13)

Given/When/Then, from the calling agent's point of view. "The tool" = the specific `paypal_*` MCP tool
named in each AC; "the service" = this MCP server as a whole.

- **AC1** (create order): Given valid PayPal credential headers and an order payload (currency, amount,
  at least one item or a flat amount), When the agent calls `paypal_create_order`, Then the tool returns
  the new order's `id` and `status` (e.g. `CREATED` or `PAYER_ACTION_REQUIRED`), and the response never
  echoes the submitted client secret.
- **AC2** (get order): Given an order id that exists on the connected account, When the agent calls
  `paypal_get_order`, Then the tool returns that order's current `status` and amount breakdown.
- **AC3** (capture order): Given an order in `APPROVED` status, When the agent calls
  `paypal_capture_order`, Then the tool returns a capture `id`, `status`, and the captured amount, which
  matches the order's amount.
- **AC4** (refund capture): Given a capture in `COMPLETED` status and a refund amount ≤ the captured
  amount, When the agent calls `paypal_refund_capture`, Then the tool returns a refund `id` and `status`.
- **AC5** (not-found mapping): Given a capture id that does not exist on the connected account, When the
  agent calls `paypal_get_capture`, Then the tool returns the service's structured `not_found` error (not
  a raw PayPal error body, not an unhandled exception / 500).
- **AC6** (missing credentials): Given one or more of the required PayPal credential headers is absent,
  When the agent calls any `paypal_*` tool, Then the service responds `401` before attempting any call to
  PayPal, and the body lists exactly which headers are required.
- **AC7** (bad credentials): Given a credential header pair PayPal itself rejects (invalid Client
  ID/Secret), When the agent calls any `paypal_*` tool, Then the tool returns the structured
  `unauthorized` error, and neither the response nor any log line contains the submitted secret.
- **AC8** (create invoice): Given a draft invoice payload with a recipient email and at least one item,
  When the agent calls `paypal_create_invoice`, Then the tool returns the new invoice's `id` in `DRAFT`
  status.
- **AC9** (send invoice): Given a draft invoice id, When the agent calls `paypal_send_invoice`, Then the
  tool returns the invoice's updated status (`SENT`, or PayPal's scheduled-send equivalent).
- **AC10** (list + pagination): Given more invoices exist on the account than the tool's default page
  size, When the agent calls `paypal_list_invoices` with no explicit limit, Then the response is capped at
  the tool's default limit and includes `has_more: true` so the agent can page further; it never returns
  an unbounded list.
- **AC11** (tenant isolation): Given two concurrent tool calls carry two different sets of PayPal
  credential headers (two different connected accounts), When both run concurrently against the same
  running container, Then each call only ever acts on, and returns data for, its own account — neither
  response, nor any log line, contains the other call's credentials or data. This is tested against the
  service's own request handling, not PayPal (PayPal has no cross-tenant concept to test).
- **AC12** (rate limiting): Given PayPal responds `429 Too Many Requests` to an upstream call, When the
  tool issues that call, Then the service retries with backoff honoring any `Retry-After` header, up to
  the configured retry budget, and — if still failing — returns the structured `rate_limited` error rather
  than crashing or hanging.
- **AC13** (idempotent create): Given the agent supplies the same caller-chosen `request_id` on two calls
  to `paypal_create_order` (or `paypal_create_invoice`), When both calls reach PayPal, Then PayPal's own
  idempotency guarantee (the `PayPal-Request-Id` header) prevents a duplicate order/invoice from being
  created — the second call returns the same object as the first.

## Tech design

### 1. Conclusion

Build a new Python/FastMCP service in the (currently empty) `paypal-mcp` repo, following
`vendor-mcp-development` SOP main line A end to end: Streamable HTTP `/mcp` + `/health`, credentials read
only from three `X-Paypal-*` request headers, request-scoped PayPal OAuth2 client-credentials token
minting (never cached across requests), and 10 tools split across two files (`orders.py` wrapping
Orders v2 + Payments v2, `invoicing.py` wrapping Invoicing v2). No existing code to build on (greenfield
repo) and no gateway/control-plane change needed — PayPal is a plain Header-credential vendor, not OAuth
user-delegation, so it fits the standard vendor-mcp contract with no network-layer exceptions.

### 2. Where the current implementation lives

Nothing — `paypal-mcp@cf7b17e` contains only `README.md`. There is no prior PayPal integration anywhere
in `MSPbotsAIFramework` or `mb-platform-agent` to build on (see "Current state" above for the org-wide
search). The nearest structural reference is any other small, already-shipped vendor-mcp repo built to the
same SOP (e.g. a `chargebee-mcp`-shaped service: Header-credential, no OAuth user flow) — new code here
should match that shape, not invent a new one.

### 3. Option analysis

| Option | What it does | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. Direct REST wrapper over PayPal's public v2 APIs (httpx) | Hand-write the OAuth2 token exchange + the ~5 REST calls this ticket needs | Small dependency surface; full control over error mapping to the SOP's fixed vocabulary; matches how other MSPbots vendor-mcp services are built | Have to hand-roll retry/backoff and token minting (small, well-understood) | **Chosen** |

| C. Ship all six capability groups (Orders, Payments, Invoicing, Subscriptions, Disputes, Payouts, Webhooks) in this first version | Matches the DEV01 BLOCKED comment's original "build from full docs" framing | One ticket, one shipped surface | ~25–30 tools (over SOP's ≤20 cap without aggressive merging), materially larger test/audit surface, and no capability beyond Orders/Invoicing is actually named anywhere in the ticket | Rejected — see Goals/Non-goals; scoped down instead |

### 5. Data & API contract

**Credential headers** (read by `app/middleware.py`, never logged, never written to disk or env):

| Header | Required | Type | Notes |
|---|---|---|---|
| `X-Paypal-Client-Id` | yes | string | PayPal REST app Client ID (PayPal Developer Dashboard → Apps & Credentials) |
| `X-Paypal-Client-Secret` | yes | password | PayPal REST app Secret, same location |
| `X-Paypal-Environment` | yes | string, enum `sandbox` \| `live`, default `sandbox` | Selects `api-m.sandbox.paypal.com` vs `api-m.paypal.com` as the upstream host |

Missing any of the three → `401`, body: `{"error": "missing_credentials", "missing_headers": [...]}`
(AC6). This is an HTTP-level rejection by the middleware, before any tool runs and before any PayPal call
is attempted — distinct from the per-tool JSON error envelope below, which only applies once a tool
actually runs.

**Upstream PayPal endpoints wrapped** (verified against `developer.paypal.com` 2026-11-02):

| Tool | Method + path | Notes |
|---|---|---|
| (internal) token mint | `POST /v1/oauth2/token`, `Authorization: Basic base64(client_id:client_secret)`, body `grant_type=client_credentials` | Response: `{access_token, token_type: "Bearer", expires_in, ...}`. Minted fresh per request (see §7), not cached across requests. |
| `paypal_create_order` | `POST /v2/checkout/orders` | Optional `PayPal-Request-Id` header = `request_id` arg (AC13). |
| `paypal_get_order` | `GET /v2/checkout/orders/{id}` | |
| `paypal_capture_order` | `POST /v2/checkout/orders/{id}/capture` | |
| `paypal_get_capture` | `GET /v2/payments/captures/{id}` | |
| `paypal_refund_capture` | `POST /v2/payments/captures/{id}/refund` | Body: `{amount?: {currency_code, value}, note_to_payer?}`; omit `amount` for a full refund. |
| `paypal_get_refund` | `GET /v2/payments/refunds/{id}` | |
| `paypal_create_invoice` | `POST /v2/invoicing/invoices` | Optional `PayPal-Request-Id` header = `request_id` arg. |
| `paypal_send_invoice` | `POST /v2/invoicing/invoices/{id}/send` | |
| `paypal_get_invoice` | `GET /v2/invoicing/invoices/{id}` | |
| `paypal_list_invoices` | `GET /v2/invoicing/invoices` | `page_size` capped at PayPal's own max (100); tool-level `limit` arg defaults to 20, hard cap 100 — never unbounded (AC10). |

**Example — `paypal_create_order`** (tool input → tool output, both JSON; this is the MCP tool's own
contract, not a new MSPbots HTTP endpoint):

```json
// input
{"currency": "USD", "amount": "25.00", "description": "Invoice #1042", "request_id": "prd21314-demo-1"}
// output
{"id": "5O190127TN364715T", "status": "CREATED"}
```

**Error envelope** (all tools, on any failure path — AC5, AC7, AC12):

```json
{"error": {"code": "not_found", "message": "No capture with id 1AB2... on this account.", "retryable": false}}
```

`code` is always one of the SOP's fixed vocabulary; tools never raise a bare Python exception back through
`tools/call` (SOP §4). Mapping: PayPal `404` → `not_found`; `401`/token-mint failure → `unauthorized`;
`422` (validation) → `invalid_argument`; `429` → `rate_limited` (after retry budget exhausted); any other
`5xx` or network failure → `upstream_error`.

**DB**: none. This service is stateless; it has no database.

**Backward compatibility**: not applicable — first version of a new vendor, nothing to stay compatible
with yet. Future tool-signature changes follow SOP §13 (breaking vs. compatible change rules).

### 6. Key flow / sequence

```
Agent → Gateway (adds X-Paypal-* headers from the tenant's stored credential) → paypal-mcp /mcp
  → middleware: all 3 headers present? no → 401 (AC6); yes → set context vars
  → tool handler (e.g. paypal_create_order)
    → paypal_client._mint_token() [POST /v1/oauth2/token, Basic(client_id:client_secret) from context]
      → PayPal 401 → map to {error: unauthorized} (AC7), do not call the target endpoint
      → PayPal 200 → access_token (kept only in this request's local scope)
    → paypal_client.request(POST /v2/checkout/orders, Bearer access_token, body)
      → PayPal 429 → retry with backoff honoring Retry-After, budget exhausted → {error: rate_limited} (AC12)
      → PayPal 2xx → map response → tool returns {id, status}
      → PayPal 4xx/5xx → map per §5 table
  → middleware finally: reset context vars (AC11)
```

### 7. Non-functional

- **Idempotency & concurrency**: PayPal access tokens are minted fresh per incoming MCP request and held
  only in that request's local scope (not the shared context vars, which hold only the raw credentials) —
  never cached across requests, even for the same tenant, because the container serves many tenants
  concurrently and a cross-request token cache is exactly the kind of shared state the three iron laws
  forbid (SOP "Operating model" section). `paypal_create_order` / `paypal_create_invoice` accept an optional caller
  `request_id`, forwarded verbatim as PayPal's own `PayPal-Request-Id` header, so a retried call from the
  agent (e.g. after a timeout) does not create a duplicate order/invoice (AC13) — idempotency is enforced
  by PayPal, not by this service.
- **Performance**: 5s connect / 30s read timeout per upstream call (SOP §5 default); one retry pass with
  backoff on `429`/`5xx`; total time for one tool call (including the token mint) budgeted under 120s.
  `paypal_list_invoices` caps `limit` at 100 and truncates with `has_more` rather than paging internally —
  the agent, not this service, decides whether to page further.
- **Security**: credentials live only in request-scoped `contextvars`, reset in `finally` (AC11); never
  written to logs, disk, or environment variables; error messages are built from PayPal's `message` field
  only, never from the request headers, so a bad secret can never be echoed back (AC7). TLS to PayPal only
  (`api-m.sandbox.paypal.com` / `api-m.paypal.com`); the service itself has no public ingress (SOP "Operating model" section).
  `gitleaks detect` run before delivery (SOP §11) since the repo will, for the first time, contain example
  credential values in README/tests — all placeholders, never real.
- **Multi-tenant isolation**: the service is stateless and has no per-tenant storage; isolation is enforced
  entirely by request-scoped `contextvars` set/reset per request (AC11) — there is no tenant identifier to
  key a cache by, because there is no cache. Two concurrent requests with different credentials are two
  independent token mints and two independent upstream calls; nothing is shared between them except the
  process's HTTP connection pool (connections carry no per-tenant state).
- **Observability**: structured JSON logs per request: trace id, tool name, upstream HTTP status, PayPal
  `debug_id` (present on PayPal error responses — the standard field support asks for), and latency; never
  the credential headers or the access token. On `upstream_error`/`rate_limited`, the `debug_id` is also
  returned in the tool's error envelope so a human can hand it to PayPal support without re-running the
  call.

### 8. Rollout & rollback

- First version of a brand-new vendor: no feature flag, no gradual rollout inside this service — nothing
  depends on it yet. Sequence (owned by the dev/review legs per `references/mcp-track.md` §3/§4, not this
  design leg): implement on `dev/PRD-21314` off `main` → gates pass → merge to `main` → because the gateway
  has never heard of `paypal` before, publish via **`/api/vendor-register`** (not `/api/deploy-int`, which
  would be `rejected` for an unregistered vendor) with:
  ```json
  {"name": "paypal", "display_name": "PayPal", "repo": "MSPbotsAIFramework/paypal-mcp",
   "credential_fields": {
     "X-Paypal-Client-Id": {"label": "Client ID", "type": "str", "required": true,
       "description": "PayPal REST app Client ID (Developer Dashboard -> Apps & Credentials)"},
  ```

- After `vendor-register` returns `ok`: check the connector wiki page for PayPal (none exists yet per the

- **Middleware tests** (`tests/test_middleware.py`): AC6 (missing header → 401 + header list), AC7 (bad

### Decisions made by DEV01

No one was available to ask (unattended design run); these are the choices made to produce a buildable
first version, each reversible by moving the ticket back to `5b - ready for groom` with the desired change
named:

- **Scope cut to Orders/Payments + Invoicing, deferring Subscriptions/Payouts/Disputes/Webhooks** — the
  ticket names no specific capability; these two groups cover the most common "act on PayPal" asks (collect
  a one-off payment, bill a customer) at roughly a third of the tool count and audit surface of covering
  all six PayPal domains named in PayPal's own API index. Alternative not chosen: ship all six domains in
  one ~25–30-tool first version (rejected — see Option C in §3).
- **10 tools, not fewer/more** — one tool per capability verb (`create`/`get`/`capture`/`refund`/`send`/
  `list`), no endpoint-for-endpoint mirroring of PayPal's finer-grained sub-resources (e.g. no separate
  "update order" or "authorize order" tool, since this ticket's flow is create → capture, not the
  authorize/capture-later variant). Alternative: also expose `paypal_authorize_order` — deferred as a
  follow-up if a use case naming the authorize flow shows up.
- **Credentials as three Headers (`Client-Id`/`Client-Secret`/`Environment`)**, not two — PayPal's
  client-credentials grant only needs `Client-Id`/`Client-Secret`, but without an explicit `Environment`
  header the service would have to guess sandbox vs. live from the credential value itself (not reliably
  possible) or hard-code one. Alternative: default silently to `sandbox` with no header — rejected because
  a silent environment default is exactly the kind of "quietly does the wrong thing in production" failure
  the audit-log requirement in the ticket's own text is trying to prevent.
- **Access token minted fresh per request, never cached across requests** — simplest way to satisfy the
  "complete request isolation" iron law with a hard guarantee rather than a time-boxed cache with an
  expiry-skew edge case. Alternative: cache the token for its `expires_in` window keyed by a hash of the
  credential, which is faster (avoids one HTTP round trip per tool call) but reintroduces exactly the kind
  of cross-request shared state the SOP's three iron laws exist to forbid; rejected.
- **`paypal_list_invoices` default limit 20, hard cap 100** — PayPal's own `page_size` maximum is 100; 20
  matches the SOP's suggested default (§2, "list tools take a `limit`, default <= 50") rounded down to a number that
  keeps a typical response well under the 20000-character budget even for invoices with several line items.
- **`destructiveHint`/`idempotentHint` annotations**: `paypal_capture_order`, `paypal_refund_capture`,
  `paypal_send_invoice` are marked `destructiveHint: true` (irreversible money movement / customer-facing
  email) and `idempotentHint: false` (a second call is rejected by PayPal, or sends a second email, rather
  than being a no-op); `paypal_create_order`/`paypal_create_invoice` are not read-only but are not marked
  destructive either (a draft/unapproved order has no side effect until captured); all `get_*`/`list_*`
  tools are `readOnlyHint: true`.

To change any of these, say so in a comment and move the ticket back to `5b - ready for groom`.

  tools instead of being duplicated in each; `tool_support.py` is the shared "build client, run,
